# 0059 Interaction to Next Paint

## Rules

- INP here is mostly the graphics chip, not the handlers: a click's paint is composited with the 3D view, so it waits for every 3D frame the chip has queued. On a slow chip Chrome queued 4-5 (0.7-2 s at 3-5 fps, software drawing); handlers are 0-2 ms. Lower INP by keeping that queue short and frames cheap; don't chase handler microseconds.
- Frames in flight (`js/render3d/gpu-pacing.js`, through `renderer.gpuBehind(n)` and `renderer.fenceFrame()`), **an A/B for now**: half of sessions (`renderer.drawPacing`, a coin in `js/main.js`; `?pacing=1`/`0` forces it; `draw_pacing` is on every event, PostHog's `$web_vitals` too) put a fence after each draw, and the render step skips the draw while the chip still has n unfinished (simulation and interface still run; the draw's dt carries in `drawDebt`, clamped to 0.1 s). n = 2 normally (`FRAMES_IN_FLIGHT`): 1 cost a fast Mac a third of its frames (60 to 40-46 fps; a fence is seldom done by the next frame), 2 measured 59 vs 59-60. After a press or a key that works the interface (`UI_KEYS`, not repeats), n = 1 for the next draw, so the queue empties and the press paints next. A fence not done after `DEAD_MS` (2 s) turns pacing off for the session (a browser whose fences never finish); a 250 ms release tried first let the queue grow back at 2-3 fps. WebGL1 has no fences: no pacing. A lost context drops the pacing with its fences. `gpu-pacing-check` holds this. Decide from the A/B (p75 `$web_vitals_INP_value` and `perf_sample.fps` by `draw_pacing`, desktop, after two weeks): keep it for everyone, or take it out.
- A frame whose draw waited isn't a frame's work: `recordCpuFrame` leaves it out of `cpu_*`, `work_p75_ms` and `autoQuality`'s step-up test (`sample.waited`), and `perf_sample.draws_waited_pct` counts them. Tools that time `requestAnimationFrame` gaps (`play-profile`) now see frames without a draw on a GPU-bound machine; `fps` in perf_sample counts real draws.
- The pacing never touches the simulation's results: headless runs never go through the frame loop, and only drawing is skipped.
- Anything that drives `renderer.draw` itself (benchmarks, the film, browser checks) is untouched; only the live frame loop paces.
- A panel of thumbnails never draws them in its handler: `thumbSrc` gives a drawn one's src or a blank with `data-thumb`, `fillThumbs(root)` draws the rest one per task after the paint, none within 400 ms of a press (`js/ui/thumbnails.js`). New panels with species or plant pictures use the same pair.
- Measuring: `nice -n 15 node tools/inp-probe.mjs [map] [quality] [years] [tries]` clicks the real controls through the DevTools protocol, so Chrome's Event Timing measures them as players' INP is measured; it prints p75 per interaction split into delay, handlers and to-paint, and the scripts in the long frames. `INP_SOFT=1` draws in software so frames run long (a stress test, not an HD 520); `INP_ROOT=<checkout>` for a before/after. CPU throttling barely slows an Apple chip's frames, so it is no stand-in for a weak laptop.
- Reporting: `js/interaction-latency.js` names each slow interaction by markup only (an id or a `data-*` attribute, `map:<tool category>`, `key:<game key>`), never page text or typed keys (`key:text`); `interaction-latency-check` holds that. Events and fields: [posthog-player-perf.md](../posthog-player-perf.md#interaction-to-next-paint-inp).
- Checks: `gpu-pacing-check`, `interaction-latency-check`, `analytics-privacy-check`, `perf-analytics-browser-check`.

## History

2026-11-27 (idea batch flight-cats, session 4; Cole asked how to improve INP). PostHog's `$web_vitals`, 30 days: desktop INP p75 606 ms, phones 560, Sumatra 1632, from players whose `perf_sample` shows a median 27 fps and a quarter under 16. On an Apple M5 every interaction measured 32-72 ms p75, nearly all of it the frame; the field guide's handler was the heaviest (17 ms, 30 at CPU x4). CPU throttling barely slowed the M5's frames, so software drawing (SwiftShader, 800x500, 3-5 fps) stood in for a GPU-bound laptop: there every click took 0.9-2.1 s, all of it "to paint". Tried first: the frame after a press runs no steps (a one-frame yield in `createFrameLoop`): no measurable gain, since the queue was the chip's, so it was dropped. One frame in flight: 16 ms paints but 25-35% fewer frames on the M5. Two in flight with the queue emptied after a press: one run gave panels 16-700 ms p75 (from 0.9-2.1 s), but repeats after the edge cases were fixed gave 0.7-2 s again with pacing on and 57% of frames waiting: software drawing runs a frame as one block of 300-400 ms, so where a click lands in it decides the wait. The frame rate is kept (59 vs 59-60 on the M5). Without a weak laptop to prove it, it ships as an A/B. Also: field-guide portraits warmed in the background were forced idle callbacks of up to 440 ms each mid-play; they now wait until 3 s after the last press. Before/after tables in `docs/ideas/2026-11-27-flight-cats/s4.md`. Not done: speed and pause still paint slowly under software drawing (1.5-1.9 s), the frame itself (the performance reviews' list), and `computeSuitability` in the field guide's handler.
